# MJ-1 sourcing evidence (`forge/sourcing.py`)

Generated by `python -m forge.sourcing --mj1` on 2026-10-17. One Crusoe call
(role `spec` = Nemotron-Super), ~$0.001. Numbers below come straight from the run;
regenerate with the same command (writes `ui/fixture/sourcing/bom.json` + `bom.png`).

## What this proves

The hard part of hardware engineering is **sourcing**: picking real vendor parts,
reading their datasheets, getting a vendor STEP (or building a dimensioned stand-in),
and checking that the number on the drawing is the number in the CAD. FORGE does that
here against the MJ-1 supersonic RC jet's real vendor registry
(`mj1/cad/kc_vendor.py`, 23 parts, STEP files in `mj1/cad/vendor/**`).

Two steps, and the tool is honest about which is which:

1. **LLM step** (Crusoe): given the mission requirements it proposes the part list
   **by category** only. It never invents a part number, mass or dimension.
2. **Deterministic step**: resolve each category to a real registry part, measure its
   dimensions **live from the STEP bounding box** (cadquery `importStep` -> `BoundingBox`),
   and cross-check the datasheet.

## 4. Envelope check (datasheet body vs live STEP bbox)

The check is **directional and real**. A faithful model's bounding box must *enclose* the
datasheet body: mounting ears, clamp bands, wire leads and connectors legitimately stick
out past the bare body, so an oversize bbox is expected, not a fault. The only true fault
is an **undersized** model whose bbox is smaller than the datasheet body (missing material).

Result on this run:

- **2 tight match** (within 2 mm): Matek H743-WING (54 x 36 x 13), Matek M10Q (the REAL STEP).
- **12 bbox encloses body** (overshoot from protruding features, expected). Examples:
  - JetCat P550: datasheet OAL 427 / dia 175; bbox 427 x 178 x 230. The +55 on the
    third axis is the two mount clamps + feet standing off the 175 mm casing (clamp feet
    reach z=115 in the drawing). Length matches the datasheet exactly.
  - KST X20 servo: datasheet case 40 x 20 x 40; bbox 55 x 20 x 46. The +15 is the mounting
    ears (55 overall per the drawing) and the output spline/boss. Width 20 matches exactly.
  - LiPo 4S: cell brick 136 x 43 x 30; bbox 192 x 43 x 30. The +56 is the XT60 pigtail and
    balance lead modelled off one end; the pack cross-section (43 x 30) matches exactly.
- **0 undersized**: no STEP is smaller than its datasheet body. Every model contains its part.
- **9 no body envelope quoted**: all GENERATED fasteners (sized by ISO head/socket
  parameters, not an L x W x H envelope) plus the RunCam Racer Nano 3, whose note quotes
  the 14 x 14 PCB but not a single overall triple, so the parser abstains rather than guess.

This is the honest version of the check: it does not flag a correct model as "wrong" just
because real mount hardware protrudes past the datasheet body.

## Honesty notes

- 21 of 23 parts are STAND-IN or GENERATED, not REAL vendor STEP. JetCat and KST publish no
  anonymous STEP (GrabCAD is login-gated), so those are accurate dimensioned stand-ins, as
  `mj1/cad/vendor/SOURCES.md` documents. The tool labels every part's `kind`; nothing is
  passed off as a vendor file that is not one.
- The envelope check validates that the stand-in CAD matches its own datasheet body, not
  that the stand-in equals an unobtainable vendor model.
- This BOM is bought-in parts only. It is not the full 25 kg aircraft mass.

## API (for the Studio / agent-manager app)

```python
from forge.sourcing import source_parts, mass_rollup, datasheet_checks
from forge.llm import LLM

llm = LLM(run_dir="runs/sourcing_mj1", budget_usd=0.5)
parts  = source_parts(requirements: dict, llm) -> list[Part]
rollup = mass_rollup(parts) -> dict
checks = datasheet_checks() -> list[dict]
```

`Part` fields: `name, vendor, function, qty, mass_g, kind, source, step,
dims_bbox_mm, dims_declared_mm, dims_status, dims_deltas_mm, note`.
`dims_status` in {`match`, `encloses`, `undersized`, `None`}.
